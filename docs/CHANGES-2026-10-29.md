## 1. What changed

### 1.1 Hardware department (new staff role and page)

Hardware is now its own department with its own staff, separate from the loading crew. It works like the Loading
page, but only for orders with **Hardwares** on them.

| Before | Now |
| ------ | --- |
| Hardwares were loaded at the **Steel** area by the loading crew | Hardwares are loaded at the new **Hardware** area by **Hardware** staff |
| 5 roles: admin, sales, loading, security, cashier | 6 roles: + **hardware** |
| Sales always pressed *Hand over to loading* | The button names where the customer goes: *Hand over to loading*, *to hardware*, or *to loading and hardware* |
| The Loading page showed every handed-over customer | Each department sees only the handed-over orders it has a part in |

The loading areas are now ([`src/data/loadingAreas.js`](../src/data/loadingAreas.js)):

| Area | Types of order | Department (staff role) |
| ---- | -------------- | ----------------------- |
| Roofings | Roofings, Roofings Accessories | loading |
| Steel | Steel | loading |
| TBA | Tire, Battery, Chassis | loading |
| **Hardware** | **Hardwares** | **hardware** |

How a customer moves through it:

- **Only Hardwares:** sales hands over → the customer waits on the **Hardware** page → Hardware calls them ("Please
  proceed to Hardware" on the display) → Done → security check at the gate.
- **Roofings + Hardwares** (or any loading area + Hardwares): the customer goes to each department in turn, in either
  order. When one department presses Done, the customer waits for the other ("Waiting for Hardware"). After the last
  area is done, they go on to the security check.
- **One place at a time:** while the loading crew has the customer, Hardware can't call or finish them (and the same
  the other way round): "Please wait until Pedro Garcia finishes."
- The Loading page no longer shows orders that are only Hardwares. The Hardware page doesn't show orders without
  Hardwares.

Where it shows in the app:

- **Sidebar:** a new **Hardware** page (under *My work → Department*) for admins and hardware staff. Hardware staff
  also get **Order status** and the **Dashboard**, like the loading crew.
- **Admin → Accounts:** a new role in the list, *Hardware: the same as loading, for the Hardware department*. An
  existing account can be moved to it too.
- **My counter (sales):** the hand-over button and dialog name the department(s), e.g. "Hand over to loading and
  hardware" and "The customer waits in line on the Loading and Hardware pages".
- **Dashboard → In charge:** a customer waiting for Hardware shows "Waiting for the Hardware crew".
- **Order status / Security:** "Waiting for Hardware" as the customer's current step.

[`src/admin/components/orders/departmentLine.jsx`](../src/admin/components/orders/departmentLine.jsx) (new, taken out

[`src/data/loadingAreas.js`](../src/data/loadingAreas.js), [`src/admin/data/loadingAreas.js`](../src/admin/data/loadingAreas.js),

#### API

| Method | Path | Who | What |
| ------ | ---- | --- | ---- |
| POST | `/admin/hardware/:queueNum/call` | admin, hardware | `{ remarks, area }`: calls a handed-over customer to Hardware; `409` if there's nothing left for Hardware on the order, or another counter has them |
| POST | `/admin/hardware/:queueNum/done` | admin, hardware | finishes the Hardware area: the order waits for its next area, or goes to the security check |
| POST | `/admin/hardware/:queueNum/back` | admin, hardware | sends the customer back to waiting |
| GET | `/admin/orders` | hardware | only today's handed-over orders with Hardwares (loading accounts: only those with a loading area) |

The `/admin/loading/...` routes work as before, but only for the loading areas.

#### Database: migration `021_hardware_staff.sql`

SQLite can't change a `CHECK` constraint, so the migration rebuilds the `users` table with `'hardware'` added to the
allowed roles and copies every row across (as migration 020 did). Sessions, orders and other tables are untouched. It
runs by itself when the server starts. `deploy/update.sh` takes a backup first.

### 1.2 API rate limiting (new)

Each computer (by IP address) can only send so many requests. Past that, the API answers **429 Too Many Requests**
with a `Retry-After` header until the time window ends. This stops a runaway screen, a script, or someone guessing
passwords from flooding the server.

| Limit | How many | Window | Applies to |
| ----- | -------- | ------ | ---------- |
| `api` | 300 requests | 1 minute | every API request except the display video (`/video/file`) |
| `orders` | 30 new tickets | 1 minute | `POST /orders` (kiosk and Customer order, which need no sign-in) |
| `failedLogins` | 10 wrong passwords | 15 minutes | `POST /auth/login`; once used up, even the right password must wait |

- A busy staff PC polls a few pages every 5–10 seconds, which is far below 300 per minute.
- A correct sign-in doesn't count against the computer.
- Messages: "Too many requests. Please wait a moment and try again." / "Too many attempts. Please wait a moment and try
  again."
- The server log shows one line per computer per window when it goes over, e.g.
  `Rate limit (failedLogins): 192.168.1.20 went over 10 in 900s`.
- **Behind nginx:** every request reaches Node from `127.0.0.1`, so the client is taken from the **last** entry of
  `X-Forwarded-For` (the one nginx adds). Entries the browser sends itself are ignored, so the limit can't be dodged
  by faking that header.
- The counts are kept in memory: **restarting the server resets them** (`sudo systemctl restart sheehan-queue`).

Files: [`server/rateLimit.js`](../server/rateLimit.js) (new), [`server/api.js`](../server/api.js).

### 1.3 Smaller fix

[`server/server.js`](../server/server.js): the built site is now sent with `pipeline()` instead of `.pipe()`. Before,
a file that disappeared halfway through sending (e.g. during a rebuild by `update.sh`) could crash the whole server.
Now only that one response is cut off.

### 1.4 Included in the same merge: payment status is set only by the cashier (`f526138`, 27 Oct)

- On **Customer order**, the payment status is grayed out. On the **Order sheet**, the *Terms* column is read-only.
- The server ignores a `paymentStatus` sent with a new or edited ticket, and refuses it on `PATCH /admin/order-sheet/:id`.
- Only the **Cashier** page (cashier and admin accounts) sets it, through `PATCH /admin/payments/:id`.

## 2. How to demo

### 2.0 Setup

Use a **test data folder**, not the live server: the demo creates tickets and accounts.

```bash
npm install
npm run dev            # http://localhost:5173  (the API is at /api)
```

Sign in at `http://localhost:5173/admin/login` with the admin from `.env` (`ADMIN_USERNAME` / `ADMIN_PASSWORD`).

Each browser **tab** signs in separately, so you can have the admin, the loading crew and Hardware open side by side
in three tabs of the same browser. Open the queue display (`http://localhost:5173/`) in a fourth tab or on a second
screen to show the calls.

Create the accounts you need in **Admin → Accounts**:

| Username | Role | Password (8+ characters) |
| -------- | ---- | ------------------------ |
| `hardware1` | Hardware | e.g. `hardware123` |
| `loading1` | Loading | e.g. `loading123` (or run `npm run seed:loading`, which makes `loading1` and `loading2` with password `loading123`) |
| `cashier1` | Cashier | e.g. `cashier123` (for demo 2.5) |

### 2.1 Demo: a customer who only bought Hardwares

1. **Admin tab → Customer order:** make a ticket with type of order **Hardwares** and an invoice number. Print or just
   save it.
2. **Admin tab → My counter:** serve the next customer. Point out that the button now says **Hand over to hardware**,
   and the dialog says "The customer waits in line on the Hardware page". Hand over.
3. **Loading tab (`loading1`) → Loading page:** the customer is **not** there. Loading has no part in this order.
4. **Hardware tab (`hardware1`):** it opens on the **Hardware** page and the customer is in line. Press **Call**. The
   one-tap message is "Please proceed to Hardware". The display shows the number with that message and reads it out.
5. Press **Done**. The customer goes on to the security check (check on the **Security** page as admin).

### 2.2 Demo: Roofings + Hardwares, two departments in turn

1. Make a ticket with **Roofings** and **Hardwares**, serve it at My counter. The button now says **Hand over to
   loading and hardware**. Hand over.
2. The customer shows on **both** the Loading and Hardware pages.
3. **Loading tab:** Call → "Please proceed to Roofings".
4. **Hardware tab:** try to Call the same customer. It's refused: **"Please wait until <loading staff name>
   finishes."** A customer is in one place at a time.
5. **Loading tab:** Done. The order shows **"Waiting for Hardware"** (Order status, Dashboard → In charge shows
   "Waiting for the Hardware crew").
6. **Hardware tab:** Call → Done. Every area is loaded, so the customer goes on to the security check.

Optional: do it the other way round. Hardware can go first, and the customer then waits for the loading crew.

### 2.3 Demo: Hardware staff can only do Hardware's work

As `hardware1`, show that the sidebar only has **Dashboard**, **Hardware**, **Order status** and **My account**. No
Customer order, Orders, Loading, Security, Cashier or Accounts. Typing `http://localhost:5173/admin/loading` in the
address bar doesn't open the Loading page (the server refuses its routes too).

### 2.4 Demo: rate limiting

Run these in **Git Bash** while `npm run dev` is running. The `X-Requested-With` header is needed by the server's
CSRF guard on `/auth/` routes.

**Wrong passwords (the clearest one to show):**

```bash
for i in $(seq 1 11); do
  curl -s -o /dev/null -w "attempt $i: %{http_code}\n" \
    -X POST http://localhost:5173/api/auth/login \
    -H "Content-Type: application/json" -H "X-Requested-With: XMLHttpRequest" \
    -H "X-Forwarded-For: 10.0.0.99" \
    -d '{"username":"admin","password":"wrong-password"}'
done
```

Expected: attempts 1–10 return **401** (wrong password), attempt 11 returns **429**. Then:

- Sign in with the **right** password from the same "computer" (`10.0.0.99`, the same curl with the right password).
  It's still **429**: it has to wait 15 minutes.
- Change the header to `X-Forwarded-For: 10.0.0.50` and sign in. It works (**200**). Other computers aren't affected.
- The terminal running `npm run dev` shows: `Rate limit (failedLogins): 10.0.0.99 went over 10 in 900s`.
- See the wait time: add `-i` to curl to see `Retry-After: <seconds>`.

> The `X-Forwarded-For` header only works here because the request comes from the same machine (like nginx on the
> server). It stands in for "another computer" in the demo. If you leave it out, the limit lands on your own PC:
> **restart `npm run dev` to reset it**.

**Too many new tickets:**

```bash
for i in $(seq 1 31); do
  curl -s -o /dev/null -w "ticket $i: %{http_code}\n" \
    -X POST http://localhost:5173/api/orders \
    -H "Content-Type: application/json" -H "X-Forwarded-For: 10.0.0.77" \
    -d '{"name":"Rate test","purpose":"Hardwares","orders":[],"invoices":[{"invoiceNo":"9000'$i'","type":"Hardwares"}],"salesman":"","team":"","pickupDate":null}'
done
```

Expected: tickets 1–30 are saved (**200**), ticket 31 is refused (**429**) and is **not** added to the queue. Note
that this really adds 30 tickets to today's queue, so only do it on test data.

If a request returns **400 Invalid order**, open Customer order in the browser and copy the body of a real
`POST /api/orders` from the browser's developer tools (Network tab) instead.

### 2.5 Demo: only the cashier sets the payment status (from `f526138`)

1. **Customer order (admin or sales):** the payment status is grayed out.
2. **Order sheet:** the *Terms* column can't be changed.
3. **Cashier tab (`cashier1`) → Cashier page:** tap a payment status (Vale, Paid, Terms, COD, Partial). It saves at
   once. Back on the Order sheet, the row shows the new terms and "Edited by" the cashier.

## 3. Deploying to the Ubuntu server

1. On the Windows PC: `git push origin master`
2. On the server:

   ```bash
   bash /opt/sheehan-queue/deploy/update.sh
   ```

   It backs up the data, pulls `master`, runs `npm ci` and `npm run build`, and restarts the service. Migration 021
   runs on the restart.
3. After it's up, in **Admin → Accounts**: create the Hardware staff accounts, or move existing loading accounts that
   work at Hardware to the **Hardware** role.

**Tell the staff:**

- Hardwares are no longer loaded at **Steel**. Orders with Hardwares go to the **Hardware** page.
- The loading crew won't see customers who only bought Hardwares.
- If someone sees "Too many attempts", they should wait 15 minutes (or ask an admin to restart the service).
